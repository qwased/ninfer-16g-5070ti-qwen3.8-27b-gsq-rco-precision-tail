# NInfer 16G · 精度尾巴版 · 可调参数说明书

适用包：`ninfer-precision-tail-package`（RTX 5070 Ti / 5080 / 5090，Windows 16GB，CUDA 13 Native 引擎 + 托盘管理器）
引擎版本：移植 **KV 精度尾巴（precision tail / KVCPT）** 后的 `ninfer-serve.exe`（`sm_120a`，CUDA 13.3 构建）
管理器：`NInferManager.exe`（本版已内置 `--kv-tail-tokens` / `--kv-tail-type` 的校验与界面）

本说明书覆盖管理网页里**每一个可调节参数**：取值范围、默认值、作用、依赖与互斥。参数改动在**下次启动模型**时生效，不会热重启正在运行的服务。

---

## 0. 这套包/这次移植新增了什么

相对上游成品（`ninfer-16g-5070ti-5080-5090-qwen3.8-27b-gsq-rco`），本包只有两类变化：

1. **引擎新增两个选项**（本移植的算法本体）：
   - `--kv-tail-tokens N`：为每个序列保留最近 `N` 个 token 的**未量化精确 K/V**（设备端影子环）。
   - `--kv-tail-type bf16|f16`：精确环的元素类型。
   其余选项与上游逐字节一致；`--kv-tail-tokens 0`（默认）时行为与移植前**完全逐字节相同**。
2. **管理器新增这两个选项的界面与校验**，并把开箱种子配置换成本包的模型与「尾巴」默认值。

精度尾巴的原理、代价、实测收益见 [第 6 节](#6-精度尾巴原理代价与实测收益)。

## 1. 目录结构与本机数据目录

程序目录（PackageRoot，可整体拷贝/迁移）：

```text
ninfer-precision-tail-package/
├─ NInferManager.exe          托盘管理程序（自包含 .NET，无需另装运行时）
├─ engine/
│  ├─ ninfer-serve.exe        CUDA 13 Native 引擎（sm_120a，含精度尾巴）
│  └─ *.dll                   FFmpeg / curl / cuBLAS / CUDA / VC 运行库，必须与 EXE 同目录
├─ model/                     放 *.ninfer 模型主文件与全部分卷（本包为空，由你自行放入）
├─ config/                    首次初始化用的“种子配置”，不是日常生效副本
│  ├─ settings.json           语言、默认配置、扫描目录、管理端口
│  ├─ profiles/*.json         两个开箱启动配置
│  ├─ chat_template.jinja      对话模板
│  ├─ chat_template.LICENSE
│  └─ device-profiles.json     GPU 内核路线校准结果（路线缓存）
├─ wwwroot/                   管理与监控网页的正式构建产物
├─ docs/                      本说明书
├─ licenses/                  NVIDIA CUDA EULA / LICENSE
├─ LICENSE                    项目许可
└─ (数据目录不在这里)
```

个人数据目录（DataRoot）：`%LOCALAPPDATA%\NInferManager\<安装位置ID>`。
ID 由程序所在**绝对路径**生成，因此**换一个位置就得到一份全新的数据目录**，首次从包内 `config/` 初始化；此后只读数据目录里的生效配置，包内种子不再覆盖它。数据目录包含：

```text
%LOCALAPPDATA%\NInferManager\<ID>/
├─ config/settings.json        生效设置
├─ config/profiles/*.json      生效启动配置（网页保存的）
├─ config/chat_template.jinja  生效模板
├─ config/device-profiles.json 生效 GPU 路线
├─ config/initialized.json     首次初始化标记
├─ config/history/             每次保存前的历史副本
├─ runtime/                    本机运行状态
└─ logs/                       引擎 stdout/stderr 与请求 JSONL 日志
```

要点：
- 网页保存的参数写在 **DataRoot**；要备份个人配置，备份 DataRoot 的 `config/`。
- `config/...` 类资源（模板、设备路线、前缀缓存文件）从 DataRoot 解析；`engine/...`、`model/...` 从 PackageRoot 解析；绝对路径保持原样。
- 相对路径的启动参数里，`--prefix-cache-file` / `--disk-kv-path` / `--request-log-jsonl` 从 DataRoot 解析。

## 2. 首次启动与开箱默认配置

1. 把模型主文件与**全部续卷**放入 `model/`（本包不附带模型）。
2. 双击 `NInferManager.exe`。它没有主窗口，图标在系统托盘；在托盘里打开「管理模型」。
3. 管理器扫描 `model/` 下的 `.ninfer` 主文件（只读容器头与分卷完整性，不加载 GPU），并把包内 `config/` 导入 DataRoot。
4. 在「模型与配置」里选中配置 → 「启动模型」→ 浏览器打开管理页（默认端口见下）。

开箱种子配置（`config/profiles/`）：

| 配置 ID | 名称 | 模型主文件 | 上下文 / KV 容量 | KV 格式 | 精度尾巴 |
|---|---|---|---|---|---|
| `gsq-vision-rk8v4-120k` | GSQ-RCO IQ3_XXS · rk8v4 · 精度尾巴 1024 · 120K | `Qwen3.8-27B-GSQ-RCO-IQ3_XXS-vision-bf16-mtp.ninfer` | 122880 / 122880 | `rk8v4` | `--kv-tail-tokens 1024 --kv-tail-type f16` |
| `gsq-iq3s-vision-rk8v4-56k` | GSQ-RCO IQ3_S · rk8v4 · 精度尾巴 1024 · 56K | `Qwen3.8-27B-GSQ-RCO-IQ3_S-vision-bf16-mtp.ninfer` | 57344 / 57344 | `rk8v4` | 同上 |

默认启动配置是 `gsq-vision-rk8v4-120k`。两个配置的其余日常参数一致：并发 1、prefill chunk 1024、MTP 草稿 4（adaptive）、ngram 31、视觉 overlay、Host cache 2048 MiB、device snapshot 1、Graph allowance 72 MiB、采样 temperature 1 / top-p 0.95 / top-k 20 / min-p 0、思考 xhigh 并保留思考。这些是**成品日常参数**，不是必须值。

> 管理网页默认端口 **8090**（见 `settings.json` 的 `webPort`）。模型 API 端口默认 **18081**（`--port`）。两者必须不同。

**改模型名怎么办**：若你放入 `model/` 的文件名与上表不同，在「模型与配置」里把「模型文件」下拉改选实际文件，保存即可；其余参数无需动。也可以新建配置。

**想换成 160K / 80K 的 nvfp4 路线**：`nvfp4` 属于「分配但惰性」的存储，精度尾巴不会与它合并，因此**不要在有意义的配置里给 nvfp4 打开尾巴**（会白占约 64 MiB 设备显存而无收益）。若需要 160K 上下文，请新建一个 `--kv-dtype nvfp4`、`--max-context 163840`、`--kv-capacity 163840`、**不填** `--kv-tail-tokens` 的配置。

## 3. 参数总览与填写规则

- 参数都以 `--名字` 形式出现在「专家 JSON」里；界面里的空值 = **不传该参数**（用引擎/管理器默认），不是传空串。
- 布尔开关（flag）：值为 `null` 表示**开启**，删除该键表示关闭。
- 管理器会**自动补齐**这几项：`--host`（默认 `127.0.0.1`）、`--port`（默认 `18081`）、`--model-id`（默认取模型文件名）、`--max-context`（默认 `163840`）、`--request-log-jsonl`（默认在 DataRoot 的 `logs/` 下按启动时间生成独立文件）。
- 管理器在保存时会校验取值与依赖（见 [第 8 节](#8-参数依赖与互斥管理器会拒绝的组合)）；非法组合会报错且**不会**写入或产生历史副本。
- 引擎单独运行时的默认值与管理器默认值不同（例如 `--port` 引擎默认 8080、`--max-context` 引擎默认 8192）。以管理器启动时以管理器的注入值为准。

## 4. 常用参数

### 4.1 API 与上下文

| 参数 | 取值 | 管理器默认 | 说明 |
|---|---|---|---|
| `--model-id` | 字符串 ≤256 | 模型文件名 | 客户端请求 `model` 字段必须匹配的名称。改它不会重命名模型文件；多个配置可共用同一名称。 |
| `--host` | `127.0.0.1` / `0.0.0.0` | `127.0.0.1` | 模型 API 监听地址。`0.0.0.0` 允许局域网访问并自动显示局域网 API 地址；不改管理网页端口，也不自动开防火墙。 |
| `--port` | 1–65535 | 18081 | 模型 API 端口。须与管理端口、`--stats-port` 及其他进程不同。改后客户端要更新 API base。0 不是自动选端口。 |
| `--max-context` | ≥1（≈1K=1024） | 163840 | 单请求总 token 上限（输入+历史+思考+回答）。不得超过模型元数据声明的上限。加大通常需要更多 KV 显存。 |
| `--kv-capacity` | ≥1 或 `auto` | 跟随上下文 | 物理 KV 池容量，按 64-token 页对齐，必须 ≥ `--max-context`。`auto` 由显存策略规划（default 按 CUDA free，strict 做驻留探测，mixed 每并发最多一个完整上下文窗口）。 |
| `--max-concurrency` | 1–8 | 1 | 同时执行的请求数。单 agent 一般 1；加大增加状态与显存开销。`--ngram-draft-tokens` >15 时必须为 1。 |
| `--default-max-tokens` | ≥0 | 0 | 请求未显式给输出上限时使用；思考+回答都计入。留空=引擎默认 8192；显式 `0`=不设独立上限（仍受剩余上下文限制）。不得大于 `--max-context`。 |
| `--stats-port` | 0–65535 | 0 | 见 5.10。 |
| `--api-key` | 字符串 | 空 | 见 5.10。 |

### 4.2 显存与缓存

| 参数 | 取值 | 管理器默认 | 说明 |
|---|---|---|---|
| `--prefill-chunk` | 128 的倍数 | 1024 | 每批读取的输入 token 数。更大可能提高预填充吞吐、增加临时显存；是否对齐还受 `NINFER_PREFILL_ALIGN` 影响。 |
| `--kv-dtype` | `bf16`/`int8`/`fp8`/`rk8v4`/`rk4v4`/`rk4v4-e8`/`rk2v4-e8`/`nvfp4`/`k8v4` | `rk8v4`（种子） | KV 缓存存储格式。`rk8v4` 是已验收路线；更粗的 `rk4v4`/`rk4v4-e8` 更省显存但精度更低。**精度尾巴只对 `bf16` 与 INT8 族生效**（见 4.3）。 |
| `--cuda-memory-policy` | `default`/`mixed`/`strict`/`strict-RESERVE-STEP` | 种子留空=default | `default`：按 CUDA free 规划、不严格驻留探测。`mixed`：允许超 CUDA free 尝试分配，显存不足时 Windows 可能用系统内存承接设备数据（驱动决定放置），可能变慢、仍可能失败。`strict`：自动选所需上下文缓存实现并做驻留探测，默认余量/步长 64/128 MiB。**mixed/strict 仅支持 Windows 单 GPU、纯文本**，且不能与显式 KV headroom、`--wddm-evictable-budget`、`--vision*`、多显卡 `--devices` 组合。 |
| `--cuda-graph-allowance-mib` | ≥0 | 72 | 容量规划里为 CUDA Graph 驱动状态预留的预算，不是 Graph 显存硬上限。`0` 表示按路线自动估算。与 `--no-cuda-graph` 互斥（关 Graph 时须为 0 或留空）。 |
| `--host-cache-mib` | ≥0 | 2048（种子） | 用 CPU 内存保存可复用 KV/状态快照（Host tier）。加大保留更多前缀，但占锁页 RAM 与传输。`0` 不建立 Host tier。与「传统缓存独立 Host 槽位/预算」（`--host-state-slots`/`--host-kv-mib`）互斥。 |
| `--device-snapshot-slots` | 1–64 | 1（种子） | 混合前缀缓存保留的 GPU 状态快照数。仅在混合缓存或 strict 下可用。 |
| `--gdn-state-fp16` | 开关 | 关 | 用 FP16 保存循环状态，减少设备/主机快照内存。改的是状态精度，不改权重。 |

> 前缀缓存路线（混合 vs 传统）由 `--use-alt-prefix-caching` / `--use-original-prefix-caching` / `--no-prefix-reuse` 与 `--cuda-memory-policy` 决定，详见 5.4。`--cuda-memory-policy strict` 会自动选择混合实现。

### 4.3 KV 精度尾巴（本移植新增）

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `--kv-tail-tokens` | 0 – 2147483647 | **0（关闭）** | 保留每序列最近 `N` 个 token 的未量化精确 K/V 到设备端影子环；attention 时对量化 body 与精确 tail 各算一次 FP32 partial，再做 online-softmax 合并。`0`=关闭，行为与移植前逐字节相同。 |
| `--kv-tail-type` | `bf16` / `f16` | `f16` | 精确环元素类型。`f16`（10 位尾数）精度更高，是默认；`bf16`（7 位尾数）是链路/对照验证形态。两者同为 16-bit，池大小、页几何与显存统计完全相同。**仅当尾巴长度 > 0 时有意义**——长度关闭时填写会被管理器拒绝。 |

生效范围（必须理解，否则会「开了没效果」）：

- **真正合并**的存储：`bf16` 与 **INT8 族**（`int8`、`rk8v4`、`rk4v4`、`rk4v4-e8`、`rk2v4-e8`）。
- **分配但惰性**的存储：`fp8`、`nvfp4`、`k8v4`（解码后的 key 处于旋转坐标系，未实现尾巴行旋转；开与关字节完全一致，**只有显存开销没有收益**）。
- **生效路由**：**small-T 解码路由**（attention query 宽度 ≤ 8）。**prefill/prompt 路由只写不合并**。
- **草稿（MTP）缓存按构造不含尾巴**：所以它只让**验证器**更准，不改变草稿路径质量。

设备常驻显存 = `round_up(N,64) × 65,536 × 并发` 字节，另有单页回滚预留（每序列 4 MiB）。实测 N=1024、并发 1：精确环 67,108,864 B（64 MiB 整），回滚预留 4,194,304 B，运行时净增 ≈ 68 MiB。

| N | 并发 1 | 并发 2 | 并发 4 | 并发 8 |
|---:|---:|---:|---:|---:|
| 512 | 32 MiB | 64 MiB | 128 MiB | 256 MiB |
| **1024** | **64 MiB** | 128 MiB | 256 MiB | 512 MiB |
| 2048 | 128 MiB | 256 MiB | 512 MiB | 1024 MiB |

代价与收益：开启后解码约 **−6%**（N=1024/并发 1，24-token 指示值）；作为对照，移植本身在尾巴关闭时解码中位 **−0.18%**。收益是「更接近不量化的分布」：decode-width KLD 在 24/24 组合下降，倍率随 body 变粗单调增大（`int8` 1.02–1.09× < `rk8v4` 2.04–2.41× < `rk4v4` 2.26–3.14× < `rk4v4-e8` 2.97–5.01×）。因此：**用最粗的能接受的 body + 尾巴**性价比最高；`rk8v4`+尾巴是本包默认。

### 4.4 草稿加速（投机解码）

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `--spec` | `mtp`/`dflash`/`dflash2` | 种子 `mtp` | 草稿后端。`mtp` 需模型内置 MTP；dflash 需对应草稿组件。**不填=关闭**（只移除后端，保留其他设置）。 |
| `--draft-tokens` | 1–15 | 种子 4 | 每轮草稿数。启用后端时必填 1–15；关闭后端时须留空或 0。 |
| `--lm-head-draft` | 开关 | 关 | 用优化 proposal head 生成草稿。当前成品配置关闭。 |
| `--adaptive-mtp` | 开关 | 种子 开 | 仅 `mtp`。按接受率与耗时在 3～上限之间调整验证草稿数；上限为 1/2 仍合法。 |
| `--mtp-attention-window` | ≥0 | 0 | MTP 草稿头只看最前 64 key 与最近 N key；主模型验证仍看全历史。0=完整历史。非零须选 `mtp`，且 ≥ 每轮草稿数+1。 |
| `--ngram-draft-tokens` | 0–63 | 种子 31 | 从历史提示/工具结果/输出复制匹配片段再与草稿一起验证。0 关闭；>15 须并发 1。启用 `--spec` 且留空时默认 15。 |
| `--ngram-min-match` | 4–64 | 12 | 触发复制所需的最短匹配长度。 |
| `--ngram-archive-mib` | ≥0 | 0 | 用 CPU 内存保存已完成请求的可复制文本，供同 `X-NInfer-Draft-Session` 复用（不是 KV 缓存）。>0 须启用复制草稿，且每会话预算在 1～总预算之间。 |
| `--ngram-session-mib` | ≥0 | 128 | 单会话可用的跨请求复制来源内存上限，不能超过总档案预算。 |
| `--ngram-native-sessions` | 开关 | 关 | 额外识别 Kilo/Codex/Claude 的会话标识；须档案预算 >0。 |
| `--lookup-ngram` | ≥0 | 0 | 用最后 N 个 token 在当前序列内查找并提议后续内容。当前路线只在 `mtp` 使用；未选 MTP 时可保存但不会生效。 |

### 4.5 图片与视频

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `--vision` | 开关 | 种子 开 | 允许图片/视频输入并加载视觉组件。模型必须含 Vision 组件；strict/mixed 显存策略只支持纯文本（种子用 default）。 |

| `--media-preprocess-threads` | 0–64 | 0（自动，最多 16） | 媒体解码/预处理线程数；不是语言模型 CPU 线程数。 |
| `--vision-offload` | `on`/`off` | — | 同义参数：`on`=`overlay`，`off`=`resident`。避免与 `--vision-residency` 填不同值。 |

### 4.7 模板与设备路线

| 参数 | 取值 | 默认 | 说明 |

## 6. 精度尾巴：原理、代价与实测收益

**原理**：量化 KV 里最新的若干行被量化误差污染，而 attention 对最近 token 最敏感。精度尾巴把「最近 N 个 token」的 K/V 不量化地存入设备端精确环；attention 时：

```
g   = max(m_b, m_t)
acc = acc_b·exp(m_b − g) + acc_t·exp(m_t − g)
l   = l_b  ·exp(m_b − g) + l_t  ·exp(m_t − g)
out = acc / l
```

即量化 body 与精确 tail 各算一次 **FP32 partial**，再做 **online-softmax 合并**（不是各自归一后相加）。写入用 fused 双写（同一次读、原值再写一份进精确环），不新增 Op 家族、不改 CUDA Graph family 序列。

**代价**：设备常驻 64 MiB（N=1024/并发 1）+ 4 MiB 回滚预留；开启后解码约 −6%。

**收益（已验收）**：

| 判据 | 结果 |
|---|---|
| 移植本身对生成结果的影响（MTP 关/开 × 视觉关/开 × ctx {8192,32768} × 8 种存储） | **64/64 逐字节相同** |
| 移植本身显存 | **64/64 逐位相同** |
| 移植本身解码 | 中位 −0.18%，**0/64 超过 2%** |
| 尾巴对 decode-width KLD 的改善 | **24/24 格下降**，倍率随 body 变粗单调增大 |
| 尾巴对 MTP 接受率 | 长提示词场景 8 格中 6 格 +2～+7 点；草稿缓存按构造无尾巴 |

**用最粗的能接受的 body + 尾巴**通常最划算：例如把 `rk8v4` 换成 `rk4v4-e8` 再开尾巴，可在接近的显存下得到明显更接近不量化分布的 K/V（ctx 8192 时 KLD 最大误差 3.38 → 0.33~0.92）。

## 7. 容量与显存规划速查

- `--kv-capacity` 必须 ≥ `--max-context`；`--default-max-tokens` 不得大于 `--max-context`。
- KV 池大小 ≈ 层数 × head_dim × kv_heads × 每 token 字节 × 容量，随 `--kv-dtype` 变化；粗化 dtype（`rk8v4`→`rk4v4`→`rk4v4-e8`）可换更大上下文。
- 精度尾巴另占 `round_up(N,64)×65,536×并发` 字节（表见 4.3）。
- 视觉组件（`--vision`）需要额外设备内存；`overlay`/`cpu` 可减少常驻。
- 前缀缓存（Host tier / snapshot）与磁盘层都**不**增加即时上下文容量，只影响复用与吞吐。
- 4090/16GB 之类的余量紧张场景：优先 `--cuda-memory-policy strict`（并关闭视觉）、降低 `--max-context`、或粗化 `--kv-dtype`。

## 8. 参数依赖与互斥（管理器会拒绝的组合）

管理器在保存时会拒绝下列非法组合（避免启动时才失败）：

- `--spec` 必须为 `mtp`/`dflash`/`dflash2`；启用后端时 `--draft-tokens` 必须 1–15；未启用时 `--draft-tokens`/`--lm-head-draft`/`--mtp-attention-window`/`--ngram-draft-tokens` 不得设置。
- `--adaptive-mtp` 与 `--mtp-attention-window` 仅 `mtp`；窗口 ≥ 草稿数 +1。
- `--ngram-archive-mib` >0 要求启用复制草稿且 `--ngram-session-mib` 在 1～总预算之间；`--ngram-native-sessions` 要求档案预算 >0。
- `--ngram-draft-tokens` >15 要求 `--max-concurrency 1`。
- `--cuda-memory-policy` 非 default 时：不得设 `--kv-headroom-mib`/`--vram-headroom-mib`，不得启用 `--vision`/`--vision-cpu`/`--wddm-evictable-budget`，不得多显卡 `--devices`。
- 混合前缀缓存（`--use-alt-prefix-caching` 或 strict）与 `--use-original-prefix-caching`/`--no-prefix-reuse` 互斥；`--device-snapshot-slots`/`--cache-taps-*`/`--prefix-cache-file` 需要混合缓存或 strict。
- `--vision-residency overlay/cpu` 要求启用 `--vision`/`--vision-cpu`；`--vision-cpu` 不与其它 residency 组合；`--vision-offload` 与所选 residency 冲突时报错。
- `--stats-port` 与 `--port` 及管理端口必须互不相同；0 表示关闭独立统计监听。
- **`--kv-tail-type` 要求 `--kv-tail-tokens > 0`**；`--kv-tail-tokens` 必须是 ≥0 的整数；`--kv-tail-type` 只能是 `bf16`/`f16`。
- `--no-cuda-graph` 时 `--cuda-graph-allowance-mib` 须为 0 或留空。
- `--no-thinking` 与 `--default-reasoning-effort` 非 `none` 冲突；`--assistant-prefill` 要求关闭思考。
- `--host-cache-mib` 与 `--host-state-slots`/`--host-kv-mib` 互斥。
